## Description
Make Edge AI Core comply fully with the Console at Rest design system v1.2 (the `console-at-rest` repo: `RULEBOOK.md`, `tokens.json`, `tokens.css`, `reference/console-at-rest.html`). Today the app is a stock Material 3 app (blue-grey palette, Roboto, 24dp cards, system icons). The owner wants proper compliance, not a recolour, in this one ticket. "Done" is the Part 10 checklist of the rule book passing for every screen.

### Approved design (2026-11-24)
1. **Stay on Views.** No Compose, no new libraries. Material 1.11.0 already has per-corner shapes, bottom sheets, snackbars, `NavigationRailView` and `NavigationView`.
2. **Token and style layer in `res/`.**
   - Day and night colours from `tokens.json` (rgba converted to ARGB), the eight spacing steps, touch sizes, per-corner shape appearances (small, control, panel, sheet), the text styles the app uses, motion durations and the three curves.
   - Fonts bundled as static TTFs in `res/font`: Sora 600/700, Instrument Sans 400/500/600, JetBrains Mono 400/500, with their licence texts.
   - `Widget.Console.*` styles for every piece used (Main, Quiet, Outline, Plain and Danger buttons, switch, pick-one circles, text box, top bar, bottom bar, rail, navigation panel, row, fold-open box, code box, notice strip, brief message, sheet).
   - The theme maps every Material 3 colour role to a token so nothing falls back to Material defaults. No `md_theme_*` names remain.
   - A JVM test compares the Android resources with a snapshot of `tokens.json` kept in the test resources and fails on drift.
   - Shadow values exist only in `tokens.css`; add them to `tokens.json` in the console-at-rest repo (with a change-log line) and mirror them here.
3. **Layouts by width.** Under 600dp: bottom bar. 600 to 1023dp: 70dp icon rail. 1024dp and over: 252dp navigation panel. Reading text capped at 704dp, settings and forms at 640dp. Edge to edge with insets; the keyboard never covers the focused field; Back returns to the Server tab before leaving the app. Each screen has a top bar with its name.
4. **Pages.**
   - Server is the app's home, an open screen: status light and word, headline and server address sit on the sphere with a fade behind each line; the reading panel starts below; the sphere drops to reading strength after 120dp of scroll.
   - Backend and Tokens are reading columns.
   - No grouping cards: sections use typewriter labels, tick rules and standard rows.
   - Tests and logs live in one fold-open box, shut by default; logs use the dark code box.
   - Three outline icons (2dp stroke, 24 grid) replace the system drawables in the navigation menu.
5. **Dot sphere.** A Canvas view ported from the reference page's script: 250 dots on a phone (600 at 1024dp and over), golden-angle placement, the five dot colours, still stars at night, leans toward touch, ripples on a commit (server start, token generated), pulses while a model loads or a test runs, drawn once and still when the system animator scale is 0, runs only while the activity is resumed. The maths lives in a plain Kotlin class with a unit test.
6. **Glass and solid.** Android 12 and later (API 31): frosted floating pieces and the lightly blurred content panel, done with a blurred copy of the sphere behind each piece (`View.setRenderEffect`); bars must not overlap scrolling content. Below API 31: the solid values. Both modes must be selectable for checking.
7. **States.** Keyboard focus ring (2dp, 2dp away, blue) on everything pressable; a reason beside every switched-off control whose cause the person can change (no model selected, server not running); busy buttons that say what they are doing; an error notice strip with one action; empty states; long paths cut with an ellipsis; nothing clipped at 200% text; no motion when the system asks for none.
8. **Behaviour the rule book requires.**
   - Confirming bottom sheets only for the irreversible (delete token, revoke access) with a named red action; the "Generate new token?" confirm is removed.
   - Brief messages (2.6 s, bottom centre) replace toasts.
   - Settings apply at once and show "Saving" then "Saved"; the context size is checked when the box loses focus, with the reason beneath it.
   - An explain card with "Not now" as an equal choice comes before each system permission prompt and the battery exemption request, asked at the point of use rather than at launch.
9. **Words.** All user-visible text moves to `strings.xml` and follows Part 9: sentence case, buttons are a verb and a thing, no "successfully", errors say what happened and what to do, statuses read like "Ready" not "Idle". To make rewording safe, `InferenceService` sends a status kind (a plain Kotlin enum with a unit test) as a new extra and `MainActivity` switches on the kind, not on words in the text.
10. **Code placement.** New Kotlin goes in new files; `MainActivity.kt` changes only where a function must change. Existing view ids stay wherever the view still exists, because `scripts/device.sh` taps by id.
11. **Docs.** Update `README.md` (tab and button names), `docs/standards/android.md` (UI section names the design system and its rules), `docs/architecture.md` (new classes), `docs/pitfalls.md` (item 15 fixed by `values-v27`), `docs/testing-on-device.md` and `scripts/device.sh` if the status log line changes.

### Approach
- **Resources first, then code.** Tokens, fonts and styles land before any layout uses them, so each later step only references names.
- **Token names mirror `tokens.json`** (`console_bg`, `console_accent_soft`, `space_4`, `radius_control_*`). Hand-written XML plus a parity test, not a generator.
- **One set of page layouts, three frames.** The three pages are separate layout files included by three activity layouts chosen by width qualifier (`layout`, `layout-w600dp`, `layout-w1024dp`). All three navigation widgets use the one menu resource; `MainActivity` gets one `showPage(itemId)` function they all call.
- **Sphere.** One plain Kotlin model owns the dots and the animation state; views only draw it. A full-screen view draws the background; on API 31 and later a second view per frosted piece draws the same model clipped to that piece with a blur `RenderEffect`. Per the reference page the content panel is lightly blurred (`panelBlur`), the navigation panel and rail are frosted (`floatBlur`), and the phone bottom bar uses the nearly solid `pop` colour, so nothing scrolls under a frosted piece.
- **Solid mode** is used below API 31, and can be forced with a launch extra on debuggable builds so it can be checked on the API 34 test emulator.
- **Status has one owner.** A plain Kotlin object, `ServerStatusStore`, holds the current status (a kind and a detail text) and the current reporter (the service instance that may report, or none), behind one lock. It is the only place a status is accepted or dropped, and the activity never writes one.
  - `begin(reporter)` makes that service instance the current reporter. `InferenceService.onStartCommand` calls it with `this` for every start that is not a stop.
  - `publish(reporter, kind, detail)` stores the status only if `reporter` is the current reporter, and says whether it did. The service sends the broadcast only when it did.
  - `stop()` clears the reporter and stores off in one step. Only the `ACTION_STOP` branch calls it, then sends the broadcast.
  - `end(reporter)` is called from `onDestroy`: if `reporter` is the current one it clears the reporter, and if the status is starting or ready it stores off (the server is gone) and the service sends the broadcast; an error stays showing; any other reporter is ignored.
  - Who wins each race: a load that finishes after a stop has no current reporter and is dropped. Stop then start on a new service instance: the new instance is the reporter, so a late publish or a late `onDestroy` from the old one is ignored. Stop then start delivered to the same instance (if Android does that): it is the reporter again, and when its still-running load finishes, "ready" is stored, which is true because the server was started again and the model is loaded. Two starts with no stop keep the same reporter. The crash-loop and missing-model exits publish their error and call `stopSelf`; `end` leaves the error showing and clears the reporter, so nothing later from that instance is stored. A destroy during a load stores off, and the load's late result is dropped. A start with no model to load (a sticky restart with nothing saved) publishes an error instead of staying at starting; the service is otherwise left as today.
  - The broadcast is only a signal: on every broadcast and in every `onResume`, `MainActivity` reads the store and applies it. Nothing else in the activity sets the status word, the switch or the test buttons' enabled state. A status reached while the app was in the background shows on return (this removes `docs/pitfalls.md` 23), and after process death the store is off, which is true. No status is kept in saved instance state. This replaces the Description's "new extra". The service keeps logging one fixed English line for `scripts/device.sh`.
- **Permission asks are separate from every action.** An explain card is an inline card with two equal buttons (the allow action and "Not now"). One plain function, `ExplainCardPolicy`, decides which card the Server page shows. The rules, in full:
  - A card shows only while the stored status kind is `READY` (the point of use: the server is running), for a permission that is missing and whose card has not been answered. Notifications count as missing only on API 33 and later, where they are a runtime permission. Notifications come before the battery exemption.
  - Any answer hides that card for good: "Not now", a denied result, or returning from the battery screen still not exempt all store an answered flag; a grant makes the permission no longer missing.
  - Both buttons are disabled from a press until its result arrives, so a request cannot be launched twice. A launch that throws (no screen can handle the battery request) is logged and counts as an answer, so the card hides.
  - Starting the server never shows or waits for a card.
  - The microphone card shows only in answer to pressing the audio test without the permission. The test starts only from the grant callback, or at once when the permission is already held. A denied result hides the card and shows a brief message that the microphone is off for the app and can be turned on in system settings.
  - The policy is recomputed whenever the status is applied (every broadcast and `onResume`) and in each result callback.
- **Bar icon colours are set in code**, not in `values-v27` as the Description's item 11 says: one place covers day, night and every API level, and it removes both lint errors of pitfall 15.
- **New UI code in new files** (`ConsoleUi.kt`, sphere classes, `ServerStatus.kt`); `MainActivity` keeps its fields and functions and changes only where behaviour changes.
- Rejected: Compose (owner rule, large rewrite); a blur library (new dependency; the only thing behind a frosted piece is the sphere); `MaterialButtonToggleGroup` for the pick-one settings (changes widget classes and selection code; styled `RadioGroup`s give the same look).

- The foreground notification's look and the launcher icon (not covered by the rule book); only the notification's wording changes.
